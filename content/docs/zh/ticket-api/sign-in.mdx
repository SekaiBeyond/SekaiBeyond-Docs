---
title: 使用彼世界账号登录
description: 让用户使用彼世界账号登录你的 Firebase 应用，并确认他们是谁。
---

SKBY Manager 等已登记的应用可以让用户使用自己的彼世界账号登录。应用无需与主站共用数据库：主站会通过 IAM 以该应用自己的服务账号身份，**为该应用自己的 Firebase 项目**签发自定义令牌（Custom Token），因此无需保存任何服务账号密钥文件。应用用一次性登录码加上只有它持有的 code verifier 换取令牌（PKCE），因此地址栏中的内容无法让任何人登录。

- **主站**告诉应用某人是谁。登录凭证只能读取这些：*主站*的数据（例如活动和团队名单）需由应用的服务器使用其 [API 密钥](./keys.mdx)读取，范围以各密钥的权限为准。
- **应用**保存自己的数据，并在自己的数据库与安全规则中决定谁能在应用内做什么，以及其用户中谁能查看密钥读取的内容。

任何已登录的本站账号都可以登录任何开启了用户登录的已登记应用，因此谁可以使用应用由应用自己决定：见[决定谁可以使用你的应用](#决定谁可以使用你的应用)。

<Steps>
<Step>

### 登记应用

在管理后台的「工具 > 应用」中登记应用，并保持勾选「用户用本站账号登录此应用」：

- **回调地址**（`redirectUris`）：1–10 个登录后可返回的地址（须为 `https://`，本地测试可用 `http://localhost` 或 `http://127.0.0.1`，且不含 `#fragment`）。这些站点上的页面也可以在浏览器中直接调用 [`POST /v1/token`](../api-reference/exchange-code.mdx) 和 [`GET /v1/me`](../api-reference/get-me.mdx)（CORS）。
- **Firebase 项目 ID** 与 **服务账号**：该应用自己的 Firebase 项目 ID（例如 `skby-manager`）以及用于签名登录凭证的服务账号（通常是其 `firebase-adminsdk` 服务账号）。

</Step>
<Step>

### 在应用的项目上授予 IAM 角色

展开「工具 > 应用」中该应用卡片下的「维护者设置说明」，在应用的 GCP/Firebase 项目中执行一次上面显示的两条 `gcloud` 命令：

1. 在应用的服务账号上授予 `roles/iam.serviceAccountTokenCreator`，以便我们的函数为该应用的项目签名自定义令牌。
2. 在应用的项目上授予 `roles/firebaseauth.admin`，以便用户在本站退出所有设备、修改密码、撤销邮箱变更或注销账号时，也能同步吊销或删除该应用项目中的对应用户。

登录需要第一项：授予之前，在 `/v1/token` 兑换登录码会以 `500 sign-in-failed` 失败。没有第二项时登录仍可用，但用户在本站的登录被终止时，应用自己的项目不会得到通知。

</Step>
<Step>

### 将用户引导至 `/authorize`

将浏览器跳转至：

```
https://sekaibeyond.com/authorize?app=<appId>&state=<state>&code_challenge=<codeChallenge>&code_challenge_method=S256&redirect_uri=<redirectUri>
```

- `app`：应用 ID。
- `state`：16–128 个字符（仅限 `A-Z`、`a-z`、`0-9`、`_` 和 `-`），每次发起登录时随机生成并保存在 `sessionStorage` 中，以便返回时核对。
- `code_challenge`：**code verifier** 的 SHA-256 的 base64url 编码（不含填充）。code verifier 是你为这次登录随机生成的 43–128 个字符（仅限 `A-Z`、`a-z`、`0-9`、`-`、`.`、`_` 和 `~`），与 `state` 一起保存在 `sessionStorage` 中。只有你的页面持有它，因此只有你的页面能兑换返回的登录码（PKCE，[RFC 7636](https://www.rfc-editor.org/rfc/rfc7636)）。
- `code_challenge_method`：`S256`，唯一支持的方式。
- `redirect_uri`：使用应用的第一个已登记回调地址时可省略；传入时必须与应用的已登记回调地址之一完全一致。

```js
// 32 个随机字节的 base64url 编码：43 个字符。
const random = () => btoa(String.fromCharCode(...crypto.getRandomValues(new Uint8Array(32))))
  .replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
const state = random();
const codeVerifier = random();
const digest = await crypto.subtle.digest('SHA-256', new TextEncoder().encode(codeVerifier));
const codeChallenge = btoa(String.fromCharCode(...new Uint8Array(digest)))
  .replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
sessionStorage.setItem('sekaiSignIn', JSON.stringify({ state, codeVerifier }));
location.assign('https://sekaibeyond.com/authorize?' + new URLSearchParams({
  app: '<appId>', state, code_challenge: codeChallenge, code_challenge_method: 'S256',
}));
```

尚未登录本站的用户会先被要求登录。随后页面会显示应用名称、维护者（如有）以及应用将能看到的内容：用户在本站的名称、头像和角色。它绝不会共享用户的邮箱或密码。在用户点击「继续」之前不会发生任何操作；点击「使用其他账号」会让用户在本站退出登录，以便换一个账号登录。

如果链接中的应用不存在或未开启用户登录、`redirect_uri` 不在该应用登记的回调地址中，或 `state`、`code_challenge` 缺失或格式不对，页面会显示「此链接无效」，不会返回任何内容。

</Step>
<Step>

### 兑换登录码、完成登录并确认用户是谁

用户点击「继续」后，`/authorize` 会跳转至：

```
<redirect_uri>#code=<code>&state=<state>
```

登录码放在 URL 片段（`#…`）中，因此绝不会通过请求地址或 `Referer` 头发送到服务器；它本身也无法让任何人登录：只能用一次，两分钟内有效，并且必须配合你的 code verifier。在你的应用中：

1. 从 `window.location.hash` 读取 `code` 和 `state`，用 `history.replaceState` 清除地址栏中的 `#…`，并核对 `state` 与保存的一致。
2. 用保存的 code verifier 在 [`POST /v1/token`](../api-reference/exchange-code.mdx) 兑换登录码：可从页面调用（在回调地址所在源，请求 `https://sekaibeyond.com/api/v1/token`），也可从你的服务器调用。响应中的 `token` 是为你的项目签发的 Firebase 自定义令牌，签发于兑换的那一刻。
3. 立即在你的应用的 Firebase Auth 实例上调用 `signInWithCustomToken(auth, token)`。此时该用户在你的项目中的 `uid` 与在 `sekaibeyond.com` 上的完全一致。

```js
const params = new URLSearchParams(location.hash.slice(1));
history.replaceState(null, '', location.pathname + location.search);
const saved = JSON.parse(sessionStorage.getItem('sekaiSignIn'));
sessionStorage.removeItem('sekaiSignIn');
if (!saved || params.get('state') !== saved.state) throw new Error('这不是本页发起的登录。');
const res = await fetch('https://sekaibeyond.com/api/v1/token', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ code: params.get('code'), codeVerifier: saved.codeVerifier }),
});
if (!res.ok) throw new Error((await res.json()).error.code);
const { token } = await res.json();
await signInWithCustomToken(auth, token);
```

4. 要确认用户在本站是谁，从浏览器（在已登记的站点上，请求 `https://sekaibeyond.com/api/v1/me`）或你的服务器（`https://sekaibeyond.com/api/v1/me` 或 `https://api.sekaibeyond.com/v1/me`）调用 [`GET /v1/me`](../api-reference/get-me.mdx)，并将该用户的 Firebase ID 令牌（`await user.getIdToken()`）放入 `Authorization` 请求头：

```js
const idToken = await auth.currentUser.getIdToken();
const res = await fetch('https://sekaibeyond.com/api/v1/me', {
  headers: { Authorization: `Bearer ${idToken}` },
});
const me = await res.json();
```

其他所有端点都需要应用的 API 密钥：用登录凭证调用会返回 `403 api-key-required`。见[读取主站数据](#读取主站数据)。

</Step>
</Steps>

## 令牌声明与实时检查

自定义令牌上的声明会保留在该次登录续期出的每一个 ID 令牌上：

- `app`：应用 ID（`appId`）。
- `group`：用户在本站的组别（`president`、`core-staff`、`staff` 或 `user`）。
- `mintedAt`：签发该次登录（即兑换登录码）时的毫秒时间戳。

声明反映的是登录时的情况。用户的组别发生变化时，会被退出你的应用，下次登录时便会带上新的组别，详见下文。

每次使用登录凭证的调用都会实时读取用户在本站的账号：

- **退出所有设备、退出其他设备、设置新密码（修改或重置）或撤销邮箱变更**后，`/api/v1` 会立即以 `401 session-ended` 拒绝该时间点之前的登录凭证。同时会吊销用户在你的应用项目中的刷新令牌，因此其在应用中的登录会在当前 ID 令牌过期后（一小时内）结束。
- **封禁账号**的效果与退出所有设备相同，立即生效；在封禁到期或被解除之前，该用户无法再登录本站或任何应用。
- **注销账号**在账号被移除时生效，即申请注销至少 48 小时之后（期间可以取消）。此后 `/api/v1` 返回 `401 session-ended`，该用户也会从你的应用项目中删除。
- **更改用户的组别**会让其退出所有应用。该用户在你的应用项目中的刷新令牌会被吊销：其在应用中的登录会在当前 ID 令牌过期后（一小时内）结束，重新登录后便会带上新的组别。`/v1/me` 会立即返回变化，`/api/v1` 也会继续接受其当前的登录。仅修改头衔，或更改其担任工作人员的活动，不会改变任何声明，也不会让任何人退出登录。
- **关闭应用的用户登录或移除应用**会在 10 秒内对 `/api/v1` 生效。
- 每位用户在每个应用中每分钟最多调用 **60 次**。

在你的应用项目中吊销和删除用户需要上面的第二项 IAM 角色。无论是否授予，`/api/v1` 都会拒绝该登录。

## 决定谁可以使用你的应用

任何拥有本站账号的人都可以登录你的应用。登录只说明某人是谁，并不代表他可以使用应用。请在你自己的项目中决定这一点，例如在数据库中维护一份访问名单，并由安全规则检查：

```
function signedInWithSekaiBeyond() {
  return request.auth != null
    && request.auth.token.firebase.sign_in_provider == 'custom'
    && request.auth.token.app == '<appId>';
}

match /projects/{projectId} {
  allow read, write: if signedInWithSekaiBeyond()
    && exists(/databases/$(database)/documents/projects/$(projectId)/access/$(request.auth.uid));
}
```

规则也可以根据令牌中的 `group` 声明按用户在本站的组别放行，或根据你的服务器用应用的密钥复制到你的数据库中的内容（例如各活动的工作人员）放行：

```
function signedInWithSekaiBeyond() {
  return request.auth != null
    && request.auth.token.firebase.sign_in_provider == 'custom'
    && request.auth.token.app == '<appId>';
}

// 在签发后 5 分钟内使用的登录；从 /v1/token 取得后立即使用的登录都是如此。被搁置更久的登录
// 可能带着某次变化之前的声明，而那次退出登录并未覆盖到它。
function usedPromptly() {
  return request.auth.token.auth_time * 1000 - request.auth.token.mintedAt < 300000;
}

// 本站的核心工作人员和会长。
function isCoreStaff() {
  return signedInWithSekaiBeyond() && usedPromptly()
    && request.auth.token.group in ['core-staff', 'president'];
}

// 本站某个活动的工作人员，且仅在活动进行期间。规则无法读取官网，因此由你的服务器
// 用应用的密钥把每个活动的开始和结束时间（GET /v1/events，存为时间戳）及其工作人员
// （GET /v1/events/{eventId}/staff）复制到你自己的数据库中。
function staffsDuring(eventId) {
  let event = get(/databases/$(database)/documents/events/$(eventId)).data;
  return signedInWithSekaiBeyond()
    && exists(/databases/$(database)/documents/events/$(eventId)/staff/$(request.auth.uid))
    && request.time >= event.startAt
    && request.time < event.endAt;
}

match /events/{eventId}/checklists/{checklistId} {
  allow read: if isCoreStaff() || staffsDuring(eventId);
}
```

- **除登录方式外，还要检查 `app`，** 这样只有为你的应用签发的登录才算数。
- **凡是检查 `group` 的地方，都要检查登录是否及时使用**（`usedPromptly`）。登录令牌签发后一小时内都有效，因此在某次变化之前签发、之后才使用的令牌，会以旧的组别开始一次登录，而任何退出登录都无法覆盖它。
- **`group` 最多可能滞后一小时。** 发生变化时用户会被退出你的应用，但其当前的 ID 令牌在过期前仍然有效，而规则无法得知它已被吊销。如果这一小时很重要（例如需要立即收回权限），请维护你自己的访问名单，或从服务器调用 [`GET /v1/me`](../api-reference/get-me.mdx) 检查。
- **如果你的项目没有授予 `roles/firebaseauth.admin`**（见上文），变化永远不会让任何人退出你的应用，`group` 会一直保持原样，直到用户重新登录。没有该角色时，不要在规则中检查它。
- **服务器复制的内容只会和你更新它的频率一样新。** 更改活动的工作人员不会让任何人退出登录，因此请按规则所需的频率重新复制，例如定时复制，并在活动开始前再复制一次。

## 读取主站数据

登录凭证只能调用 [`GET /v1/me`](../api-reference/get-me.mdx)。活动、团队名单、活动工作人员和订单都需由你的服务器使用应用下的 [API 密钥](./keys.mdx)读取，范围以该密钥的权限为准。无论谁在使用你的应用，密钥读到的内容都一样（包括未发布的活动），因此你的应用需自行决定其用户中谁能查看哪些内容，例如根据登录凭证中的 `group` 或你自己的访问名单。
