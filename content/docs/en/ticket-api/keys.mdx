Core-staff and above register apps and manage their server API keys in the admin panel under **Tools > Apps**. The staff group can't see that tool, and the functions behind it (`listApps`, `saveApp`, `deleteApp`, `createApiKey`, `renameApiKey`, `revokeApiKey`) refuse anyone below core-staff.

## Registered apps

Every integration starts with a registered app (`apps/{appId}`):

- **App ID** (`appId`): 1–32 lowercase letters, digits and `-`, such as `wxapp` or `skby-manager`. It's used in sign-in links and to keep the app's ticket orders separate from other apps', so it can't change once registered.
- **Name and owner**: shown on the list and when people sign in to the app. The owner is an optional account on the site.
- **User sign-in** (optional): redirect URIs, person scopes, Firebase project ID and service account for signing people in at `/authorize` (see [Sign in with Sekai Beyond](./sign-in.mdx)). Leave unticked for a server-only app that only uses API keys.
- **Removing an app** stops sign-in to it and revokes and deletes all of its API keys in the same transaction.

## Server API keys

On any registered app's card, **+ New Key** creates a server-to-server key under that app:

- A key is shown once, when it's made. Only its SHA-256 is stored, in `apiKeys`, which no client can read (see [`firestore.rules`](https://github.com/SekaiBeyond/SekaiBeyond-Web/blob/main/firestore.rules)). A lost key can't be recovered: click **Re-create** on the old key to make a new one with the same settings under the same app, then revoke the old one.
- **A new key works within a few seconds of being made,** not at once. Until then it answers `invalid-api-key`, so a first call made straight away may need a retry.
- **Revoking a key deletes it.** It stops working at once and leaves the list, and Records keep its name, its app and its first and last few characters. An expired key gets a Delete button to clear it from the list the same way.
- Each key has **scopes**: `events:read`, `tickets:write`, `tickets:read`.
- A key can be held to **specific events**, up to 20 of them, archived or not. By default it can use every event.
- **Orders are kept per app ID** (`appId`). Two apps can each have an order `1001`, and a key only places and reads its own app's orders. Every key created under the same app shares those orders, so a replacement key under the same app finds the orders placed before.
- Every key **expires**, after one year by default and two years at most.
- Keys belong to the app, not to whoever made them. A key keeps working after its maker steps down, and any core-staff can rename or revoke it. Renaming changes only what the list, new orders and new records call it: orders and records already made keep the name they were made under.
- Each key may make **120 calls a minute**.
- Registering, editing or removing an app, creating, renaming or revoking a key, every order placed and every email sent or queued for one are logged in **Records**.

<Callout type="error" title="The key belongs on the app's server only.">
  Never put it in a mobile app, mini-program or web page: anyone could pull it out, read everything it can, and issue themselves tickets. Answers to calls made with a key never carry CORS headers.
</Callout>

## Key scopes

| Scope | Lets the key |
|---|---|
| `events:read` | [List events](../api-reference/list-events.mdx) and [get an event](../api-reference/get-event.mdx) |
| `tickets:write` | [Create an order](../api-reference/create-order.mdx) |
| `tickets:read` | [Get an order](../api-reference/get-order.mdx) |

A call without the scope it needs answers `403 missing-scope`. Calling a person route (`/v1/me`, `/v1/team`, `/v1/events/{eventId}/staff`) with a key answers `403 sign-in-required`. One over the rate limit answers `429 rate-limited`, with `Retry-After` saying how many seconds to wait. See [Errors](../api-reference/errors.mdx).
